Scenario Understanding & Solution Design

20% of total score
Problem Interpretation Full marks expected
How did you understand the problem?
The task is to predict a continuous flood risk score (0–1) for Sri Lankan locations and deploy it as a production service. The custom metric is 0.5·MAE + 0.5·RMSE × (1 + max(0, 1−EV)) — it penalises both error magnitude and unexplained variance equally, which pushed us to balance accuracy with prediction coverage. We implemented the exact metric in src/train.py so every evaluation run uses the same formula as the leaderboard.
What were the key constraints?
Three constraints shaped every decision: (1) Real-time inference — a deployed API must score a single new record in milliseconds, ruling out pseudo-labeling or multi-seed ensembles that need the full test set. (2) Reproducibility — the same model must retrain from scratch and produce consistent artifacts. (3) Production reliability — the service must keep working even without an external API key (LLM falls back to a template).
Solution Strategy & Design Alignment Full marks expected
How did you design the solution to match the problem?
We separated the system into three clean layers: offline training (produces versioned model artifacts), online inference (loads those artifacts and scores single records), and monitoring (logs every prediction and surfaces drift). This architecture means we can retrain the model without changing the API, and we can upgrade the API without retraining.
Why an ensemble rather than a single model?
Each model captures different signal: LightGBM is fast and good on dense numeric features, CatBoost handles categoricals natively (district, landcover, soil type) without label encoding, XGBoost adds a third independent learner. The Ridge meta-stack then learns the optimal combination from out-of-fold predictions — if one model overfits a fold, the others compensate.

Evaluation Methods Strong
How did you validate the model?
5-fold cross-validation with out-of-fold (OOF) predictions. The Ridge meta-learner is trained on OOF scores — not on re-predictions from the full training data — which prevents leakage. We track per-fold metrics and the OOF aggregate in MLflow so we can compare runs. The calibration shift is also computed on OOF predictions to avoid inflating performance.
# Custom metric — implemented exactly as the leaderboard formula def custom_metric(y_true, y_pred): mae = mean_absolute_error(y_true, y_pred) rmse = sqrt(mean((y_true - y_pred)**2)) ev = explained_variance_score(y_true, y_pred) return 0.5 * mae + 0.5 * rmse * (1 + max(0.0, 1.0 - ev))
Code Quality Strong
  • Modular structure: config.py / data_validation.py / features.py / train.py / inference.py — each file has one clear responsibility.
  • Test suite: 3 pytest files covering features, inference, and the API. Run with a single pytest -v command.
  • Type-annotated: Pydantic schemas for all API request/response models, mypy-friendly source files.
  • No global state: FeatureEngineer is a fit/transform object; FloodRiskPredictor is a loadable class. Both are stateless at inference time.

MLOps & Production Readiness

25% of total score
Deployment Approach Full
How did you deploy the system?
Single Docker image using a multi-stage build: Stage 1 (Node 22) compiles the React frontend; Stage 2 (Python 3.11-slim) installs the ML dependencies and copies the trained model artifacts. The FastAPI app serves both the REST API and the pre-built frontend static files from one process. This means one image, one URL, one deployment command.
# Multi-stage Dockerfile (simplified) FROM node:22-slim AS frontend-build RUN npm ci && npm run build # produces frontend/dist/ FROM python:3.11-slim COPY requirements-app.txt . RUN pip install -r requirements-app.txt COPY src/ app/ models/ . COPY --from=frontend-build /app/frontend/dist/ frontend/dist/ CMD uvicorn app.main:app --host 0.0.0.0 --port $PORT
Live at: https://floodguard-production.up.railway.app — the same URL serves the web UI, the API (/predict, /health), and the monitoring dashboard (/dashboard).
Automation — CI/CD & MLflow Full
What automation did you put in place?
GitHub Actions CI runs on every push to master: installs dependencies, runs the full pytest suite, then builds the Docker image. If tests fail, the Docker build is blocked. This catches regressions before they reach production.
How do you track model experiments?
MLflow (local file store in mlruns/) logs every training run: hyperparameters for all three models, per-fold custom metric, OOF aggregate metric, calibration shift, and the metadata.json artifact. You can inspect all runs with mlflow ui --backend-store-uri ./mlruns.
Monitoring & Reliability Full
How do you monitor the live system?
Every /predict call is logged to SQLite (monitoring.db): raw inputs, flood risk score, risk category, model version, latency in ms, and OOD flag count. The /dashboard page visualises prediction volume over time, score distribution, risk-category breakdown, top districts, and average latency. A separate /feedback endpoint lets users report whether flooding actually occurred.
How do you handle out-of-distribution inputs?
src/data_validation.py computes training-data ranges at fit time and checks each inference request against them. Any field outside the expected range raises an OOD flag, which is returned in the API response and logged. The UI shows these flags to the user as a warning — the prediction still runs, but the user is told to treat it with caution.
Scalability Considerations Acknowledge honestly
Be proactive about this: If judges ask about scalability, acknowledge SQLite honestly and explain the upgrade path. Don't wait to be caught.
What are the scalability limits of your current system?
The FastAPI service itself is stateless and horizontally scalable — you could run 10 replicas behind a load balancer with no code changes. The current bottleneck is SQLite for monitoring, which supports only one writer at a time. For production at scale, we'd replace it with PostgreSQL (a single config change since we use raw SQL through Python's DB-API). The ML inference itself is well under 50 ms per request, well within any real-world SLA.

Innovation & Problem Solving

10% of total score
Creative Features Beyond the Baseline Strong
  • AI-generated risk reports (GPT-4o-mini): Every prediction includes a plain-language summary and 4–5 concrete recommendations written by GPT-4o-mini. If the API key is unavailable, a deterministic template kicks in automatically — the system never fails because of an external dependency.
  • Live weather integration (Open-Meteo): The /live-risks endpoint fetches real 7-day rainfall for every district from the Open-Meteo free API and re-scores each district with live data, showing how current weather shifts flood risk above or below the typical baseline.
  • Flood alerts system (/alerts): Districts where live rainfall has elevated risk to High or Severe are surfaced as active alerts — a safety-oriented feature that goes beyond pure prediction.
  • Mobile app (React Native / Expo): A full iOS/Android app mirrors the web frontend — Predict form, AI report, monitoring dashboard — connecting to the same live backend.
Engineering Trade-offs — the strongest innovation story Very strong
What was the most important engineering decision you made?
The biggest trade-off was research-prototype vs. production-deployable model. Our Initial Round solution (solution_v10.py) scored ~0.383 on the leaderboard using 5 models, 10-fold × 3-seed CV, pseudo-labeling, and mean calibration — but it required the entire test set to be available at once and took several minutes to run. That architecture is impossible to deploy as a live API.

For FloodGuard AI we deliberately reduced complexity: 3 models, 5-fold CV, fixed hyperparameters, no pseudo-labeling. We kept the ideas that survived productionisation (ensemble + Ridge meta-stack + calibration) and dropped the ones that didn't (pseudo-labeling, multi-seed search). The result trains in 45 seconds and scores any single new record in under 50 ms.
Key phrase for the viva: "We consciously traded 2–3 points of accuracy for a 100× faster inference pipeline that can actually serve a real user. A deployed model that works is worth more than a research model that can't be productionised."
Synthetic lat/lon insight Good debugging story
Did you find any data quality issues?
Yes — we discovered that the latitude and longitude columns in train.csv are randomly generated and uncorrelated with district. A model that naively trusted them would learn random noise. Our fix: we replaced them with hardcoded real district centroids in the feature pipeline (e.g. Colombo → 6.93°N, 79.85°E). This gave the model meaningful geographic signal and improved OOF performance.

Viva Evaluation

15% of total score
Tough questions you must be ready for Practice these out loud
Why did you use three models instead of one? Isn't that overkill?
Each model has a different inductive bias. LightGBM excels on dense numeric features with leaf-wise growth. CatBoost handles categoricals natively without label encoding. XGBoost provides a third independent perspective. Their errors are partially uncorrelated, so blending them via Ridge reduces variance. The cost is ~3× training time, but training takes only 45 seconds — a cheap price for a measurable improvement.
What is Ridge meta-stacking and why not just average the predictions?
Simple averaging assumes all models are equally good. Ridge regression on OOF predictions learns the optimal weights from data — and it found that CatBoost (0.713) is far more reliable than XGBoost (0.134) on this dataset. A simple average would have over-weighted the weaker model and hurt performance.
What does "out-of-fold" mean and why does it matter?
In 5-fold CV, each training example is predicted once by a model that was trained on the other four folds — so it never saw that example during training. These OOF predictions are unbiased estimates of how the model generalises. We train the Ridge meta-learner on these OOF scores, not on re-predictions from the full data, which would cause target leakage and inflate performance.
What would you do differently if you had more time?
Three things: (1) Add the pseudo-labeling pass from our Initial Round solution — it consistently improved leaderboard scores by ~0.01. (2) Replace SQLite with PostgreSQL for production-grade monitoring. (3) Add automated retraining: a scheduled job that retrains the model when the monitoring dashboard detects significant score distribution drift.
Your model scores 0.41 on OOF. How close is that to the best submission?
The best leaderboard score was approximately 0.383. Our OOF metric of 0.4071 is on the full training set without pseudo-labeling or multi-seed ensembling — the gap is expected. More importantly, the goal of FloodGuard AI was to produce a deployable service, not to maximise leaderboard score at the cost of serving capability.
How does your monitoring detect model drift?
Currently we log prediction score distributions and latency over time. The dashboard shows the score histogram across all recent predictions — if the distribution shifts significantly (e.g. far more High/Severe predictions than usual), that's a signal of input distribution shift. A production next step would be a statistical test (KS-test on score distributions) that triggers an alert automatically.

Real Debugging Stories

Use these to demonstrate debugging insight in Criterion 5
Bug 1 — AI report not working in productionSolved
  • Symptom: API kept returning "source": "template" instead of "source": "llm", even with the OpenAI key set.
  • Investigation: Added a temporary print(f"LLM error: {exc}") to the exception handler and deployed. Railway logs immediately showed: TypeError: Client.__init__() got an unexpected keyword argument 'proxies'.
  • Root cause: openai==1.51.0 internally passes proxies= to httpx.Client(), but Docker's pip pulled httpx>=0.28 which removed that parameter.
  • Fix: Upgraded to openai==1.57.0 and pinned httpx<0.28 in requirements-app.txt.
  • Lesson: Never silence exceptions completely in production code — always log at minimum the exception type so you can diagnose remotely.
Bug 2 — CI failing on static files mountSolved
  • Symptom: GitHub Actions test job failed with RuntimeError: Directory 'frontend/dist/assets' does not exist.
  • Root cause: app.mount("/assets", StaticFiles(...)) ran at module import time. In CI, npm hasn't built the frontend, so the directory doesn't exist when pytest imports app.main.
  • Fix: Wrapped the mount in if (FRONTEND_DIST / "assets").exists(): — mount only happens when the build exists.
  • Lesson: Code that runs at import time must be safe to execute in all environments (test, Docker, dev), not just the production container.
Bug 3 — Synthetic lat/lon in training dataSolved
  • Discovery: Noticed that lat/lon values were uncorrelated with district — two records in Colombo could have completely different coordinates hundreds of km apart.
  • Impact: Any model feature using raw lat/lon (KNN lookups, haversine distances) would learn random noise instead of genuine geography.
  • Fix: Replaced raw lat/lon with hardcoded real district centroids in the FeatureEngineer. Features like distance-to-coast and haversine-KNN now use geographically correct coordinates.
